# 1. תשובות ידניות ב־Railway — 10.09.2026

1.1 G04 מוסיף מענה טקסט ב־Inbox דרך `conversations.reply.send`. ה־Web משתמש ב־Server Action וב־API המאומת הקיימים. אין גישת Meta או מסד נתונים מהדפדפן. מתג `MANUAL_REPLY_ENABLED` כבוי כברירת מחדל.

1.2 מסלול השליחה: בקשה קבועה → הרשאה ו־Tenant → Quota → טרנזקציה עם Outbox, גרסת שיחה, Receipt ו־Audit → Worker → שמירת מכסת Service Reply → Credential Vault → בדיקת הרשאה נוספת ו־Seal → Meta POST יחיד → הודעה עם מזהה ספק אמיתי → עדכוני מסירה קיימים.

# 2. זהות, הרשאות וחלון שירות

2.1 הטקסט נשמר כפי שנכתב, עד 4,096 יחידות UTF-16, בלי תווי בקרה מסוכנים או Unicode פגום. אין מדיה או כפתורים במסלול זה. לא השתנו מגבלות Meta; הבסיס הוא החוזה הקיים ב־Meta Bot Reply וב־[מסמך מגבלות WhatsApp](whatsapp-rate-limits.md).

2.2 רק owner/manager/agent פעיל עם `conversations.reply` רשאי להשיב, ורק לשיחה שאינה סגורה ושמשויכת אליו. שיוך נדרש לפני שליחה. איש קשר עם הסכמה withdrawn חסום. תגובת שירות ללקוח בתוך החלון אינה יוצרת הסכמה שיווקית ואינה משנה את רשומת ההסכמה.

2.3 חלון השירות נגזר ב־PostgreSQL מההודעה הנכנסת האחרונה שאינה בעתיד. נדרש חלון תקף בזמן השמירה ושוב ברגע ה־Seal. חלון שנשמר אינו מוארך אוטומטית על סמך הודעות מאוחרות. מחוץ לחלון נדרשת תבנית מאושרת במסלול הקיים.

2.4 המזהה נגזר מהבקשה, השיחה, גרסת השיחה, ה־Tenant והנציג. אין מזהים אקראיים. ניסיון חוזר באותו Payload מחזיר Receipt קיים אחרי בדיקת הרשאה עדכנית. החלפת נציג אינה מאפשרת לקרוא Receipt של נציג אחר. גרסה ישנה נדחית.

2.5 מותרת תשובה אחת שלא הסתיימה לכל שיחה, כולל `unknown`. אינדקס ייחודי במסד אוכף זאת גם בין כמה תהליכים. אחרי אובדן תשובה מה־API, ה־Composer שומר את הבקשה המקורית ומנסה לאמת אותה מחדש, בלי להשתמש בגרסה חדשה מה־Polling.

# 3. Worker והתאוששות

3.1 המיגרציה `0073_manual_reply_outbox.sql` מוסיפה תור PostgreSQL ייעודי. אין Bot Flow פיקטיבי ואין מזהה ספק לפני קבלת מזהה אמיתי. נציג רואה queued/preparing/sending/failed/unknown; אחרי קבלה מוצגת הודעת ה־Inbox הרגילה.

3.2 Worker עצמאי בודק עבודה פעם בשנייה כשהוא פנוי, Claim אחד בכל פעם. זהו מרווח בדיקה מקומי ואינו SLA. `FOR UPDATE SKIP LOCKED` מתאם תהליכים. Claim של preparing תקף ל־60 שניות; פקיעתו מאפשרת דור חדש וחוסמת את העובד הישן. Shutdown ממתין לעבודה הפעילה לפני סגירת החיבור למסד.

3.3 Admission משתמש במכסת Service Reply הקיימת, עם אותם מפתחות Sender/Recipient שמשמשים בוט וקמפיינים. מזהי Reservation מופרדים לפי סוג השליחה ודור ה־Claim. לא הומצאו מכסות או ערכי ספק חדשים.

3.4 לפני ה־POST, ה־Seal נועל הרשאות ובודק שוב Tenant, חברות ותפקיד, שיוך, איש קשר וגרסתו, חלון שירות, חיבור Meta וגרסתו, ו־Credential revision/digest. גם אירוע המדיניות המקורי חייב להיות עדיין הפעיל, עם ראיות בתוקף. התחלת שליחה שננעלה לפני ביטול הרשאה יכולה להשלים; קבלה אמיתית נרשמת גם אחרי הביטול.

3.5 `sending` אינו ניתן לתביעה חוזרת. קריסה, אובדן תגובה, 5xx או כשל שמירת קבלה נשארים `unknown`, ללא שליחה נוספת וללא שחרור מכסה כאילו לא נשלח. תחזוקה מסמנת sending ישן כ־unknown אחרי שתי דקות, במנות של עד 100. 4xx מפורש עוצר את ההודעה; Cooldown מוכח נשמר בבקרת הקצב המשותפת לפי המדיניות הקיימת. אין Retry אוטומטי של POST שנשלח.

3.6 אחרי קבלה נשמרת הודעה אחת עם provider_message_id אמיתי. עדכוני sent/delivered/read/failed משתמשים במנגנון Webhook הקיים. מצב waiting_for_contact נקבע רק אם לא הגיעה הודעה חדשה ולא השתנה השיוך בזמן השליחה.

3.7 **תפעול unknown:** אין כפתור ביטול, Retry או שחרור חסימה של unknown במוצר. יש לבדוק מול נתוני הספק ולהסלים למפעיל. אסור להמציא provider_message_id, למחוק שורת Outbox או לשנות אותה ל־queued. מתודת `accepted` הפנימית יכולה לשמור קבלה מאוחרת עם מזהה ספק מוכח; אינה API ציבורי ואינה הוכחת התאוששות מול Meta. התאוששות כאשר תגובת הספק אבדה עדיין דורשת תרגול קבלה חי ואינה מוכרזת כמוכחת.

# 4. פריסה ובדיקות קבלה

4.1 להחיל את כל 74 המיגרציות ב־Staging. לאחר מכן לפרוס Worker תואם → API → Web מאותו Release. Worker קודם לפעולת השליחה. הגרסה אינה מוחקת או משנה נתוני D1.

4.2 הפעלה מבוקרת ב־Staging דורשת `MANUAL_REPLY_ENABLED=true` גם ב־API וגם ב־Worker, Graph API version מפורשת, מפתח ההצפנה ומפתח HMAC קיימים, חיבור Meta תקף ומדיניות Rate Limit פעילה ומאומתת. תצורה חלקית נדחית לפני פתיחת Pool. המתג אינו מוכיח שה־Worker השני בריא; יש לוודא זהות Release ובריאות בפועל. אין לשים מפתחות במשתני NEXT_PUBLIC.

4.3 לפני Production: לבדוק שליחה ומסירה אמיתית, חלון שירות סגור, opt-out, שיוך והרשאות, חידוש חיבור, מגבלת קצב, הפעלה מחדש ואובדן תגובה. יש להוכיח גם את מסלול הטיפול ב־unknown ואת ה־UI בעברית/אנגלית/ערבית. בדיקות המקומיות ו־CI אינן מחליפות זאת.

4.4 בכיבוי: להשבית יצירה חדשה ב־API, להפסיק Worker בצורה נקייה, ולבדוק queued/preparing/sending/unknown. אין לרדת לגרסה שאינה מכירה את הטבלה ולהכריז שההודעות הסתיימו. התור נשאר במסד, בלי שליחה אוטומטית בזמן שהמתג כבוי.

4.5 בדיקות: `tests/manual-reply-worker.test.mjs`, חוזי API/Handler, ו־`tests/integration/manual-replies-postgres.test.mjs`. CI מפעיל PostgreSQL 17.11 נפרד לתרחישים אלה. נתוני הבדיקות הם Fixtures קיימים; לא נוצרו רשומות לקוח או הודעות הדגמה במוצר.


# 5. תיאום ה־Inbox ושימור בקשות — 10.09.2026

5.1 הטיוטה וה־Payload המקורי נשמרים ברכיב ה־Inbox גם כשסינון מסיר את ה־Composer. מעבר בין שיחות אינו מחליף את בקשת הניסיון החוזר בגרסת שיחה חדשה. לא נשמר תוכן ב־localStorage; יציאה מה־Inbox או טעינת עמוד מחדש אינן מכוסות בשימור המקומי.

5.2 Polling ופעולות משתמש תופסים אותו מנגנון לפני קריאת Server Action. המענה מחזיק אותו עד קריאת האישור. כשל בקריאה לאחר שמירה שאושרה משאיר את המשוב כאישור ומאפשר ל־Polling להשלים את הקריאה; אינו משחזר את פקודת השליחה. הרשאות ו־Version עדיין נאכפים בשרת.

5.3 בדיקות Promise מושהות מאמתות ניסיון כפול, בקשה לא מאושרת לאחר שינוי גרסה, קריאת אישור שנכשלה ושחרור כפול. אין בכך בדיקת דפדפן, ספק חי או פתרון לאובדן provider_message_id לאחר POST.
