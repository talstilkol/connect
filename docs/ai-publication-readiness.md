# 1. מוכנות לפרסום AI — R216, 11.09.2026

1.1 C4.1.1 ממומש ונבדק מקומית. גם מסך פרטי הסוכן וגם פעולת הפרסום משתמשים ב־PostgreSQL לבדיקת התנאים העדכניים. הפרסום אינו חסום עוד על ידי Provider שמחזיר false באופן קבוע. אין הפעלה של חשבון ספק או פריסה בסבב הזה.

1.2 פרסום אינו אישור שהחשבון החיצוני קיבל בקשה. דיווח Worker מעיד שהתהליך התחיל עם רכיבי התוכנה הנדרשים ותצורה תקינה לפי הבדיקות המקומיות. אישור המודל לאחר Eval, אימות מחירון אמיתי, הרשאות החשבון וקבלת Meta/OpenAI חיים נשארים לשלב החיבורים.

# 2. דיווח Worker וגבולות התוקף

2.1 מיגרציה 0083 מוסיפה ai_runtime_worker_health. כל Worker שבו AI_RESPONSES_ENABLED=true מדווח תחת RAILWAY_WORKER_SCHEDULER_OWNER_KEY הקיים, אחרי התחלת התורים וה־Scheduler ובהמשך בכל מחזור התחזוקה שלו. הדיווח חיובי רק כאשר תצורת Responses תקינה, המחירון בתוקף, קליטת Meta מורכבת, ושליחת תשובות AI ומענה ידני מופעלים. מזהה ה־Worker חייב להיות ייחודי בין תהליכים מקבילים לפי חוזה ה־Scheduler הקיים.

2.2 ה־API מקבל רק מצב מוכנות, מזהה Worker, תפוגת מחירון וזמן מסד. API key, מודל, מחירון מלא ונתוני לקוחות אינם נשמרים בטבלה ואינם עוברים ל־API או לדפדפן. מסלול HTTP אינו מאפשר ללקוח להזין דיווח מוכנות.

2.3 נדרש דיווח מה־90 שניות האחרונות לפי שעון המסד. אין דיווח טרי, מחירון שפג, דיווח עתידי או Worker לא מוכן שוללים את המוכנות. אם כמה Workers מדווחים במקביל, כולם חייבים להיות מוכנים. כיבוי מסודר מסיר את הדיווח של אותו Worker; בקריסה או כשל תחזוקה הדיווח פג. זהו חלון טריות של Connect, לא SLA של ספק ולא ניטור רציף של זמינות חיצונית.

2.4 תצורה שהשתנתה דורשת הפעלה מחדש לפי תהליך הפריסה. יש לפרוס תחילה את 0083, אחריה API ו־Worker מאותה גרסה, ולהשאיר הפעלת AI כבויה עד השלמת קבלת הספק. אין להעתיק מפתחות Responses אל סביבת ה־API לצורך בדיקת מוכנות זו.

# 3. תנאי הפרסום והאטומיות

3.1 נדרשים משתמש פעיל עם הרשאת Owner או Manager בעסק, זכאות ביצוע נוכחית, תקציב חיובי ב־USD, מצב agent-approval, הודעת העברה לנציג, נציג פעיל ומקורות מוכנים. מגבלת העלות נקובה בסנטים: 100 יחידות הן דולר אחד. אין המרת ILS או פרסום מצב automatic בגרסה הזו. טיוטות ישנות נשמרות ויכולות לעבור תיקון מפורש.

3.2 נעילת העסק קודמת לבדיקת המשתמש, לרישום Receipt ולנעילת המקורות. בדיקות המוכנות בפרסום רצות באותה טרנזקציה ובאותו חיבור מסד כמו שינוי הסוכן, גרסתו, ה־Audit וה־Receipt. אין שימוש ב־Pool חיצוני לבדיקת הרשאות בתוך הפעולה.

3.3 המוכנות נבדקת שוב אחרי המתנה על נעילת הסוכן. אם Worker חדל להיות מוכן או המחירון/הזכאות פגו בזמן ההמתנה, כל הפרסום מתבטל. כשל בכתיבת Audit מבטל גם גרסה שפורסמה ושינוי ל־active; אין Receipt מוצלח חלקי. לחיצה חוזרת על בקשה שכבר הושלמה מחזירה את ה־Receipt הקיים, ללא פרסום נוסף.

3.4 ה־UI מסביר את תנאי USD ואישור נציג בשלוש השפות. automatic מוצג כאפשרות שאינה זמינה בגרסה זו. תוצאת מוכנות היא צילום מצב בזמן הקריאה; לחיצה על פרסום מבצעת שוב את הבדיקות בצד השרת. בדיקות תקציב, זכאות, מקורות, אדם מאשר, חלון שירות והרשאות ספק ממשיכות גם בגבולות הביצוע עצמם.
