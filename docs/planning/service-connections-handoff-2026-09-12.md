# 1. חיבורים מרוכזים — לאחר סגירת הקוד

1.1 מסמך זה מרכז את שלב החיבורים שבתוכנית הקיימת. הוא אינו הוכחה שהחשבונות מחוברים ואינו מבקש התחברות עכשיו. פרטי הדומיין והרשאות החשבונות הנוכחיים לא אומתו בסבב R220. נבדוק את המשאבים הקיימים לפני יצירת משאב נוסף; לא מכניסים סודות למסמך או להודעה.

| סדר | שירות | מה נדרש לבדוק ולהגדיר | תנאי סיום |
|---|---|---|---|
| 1 | GitHub | גישה למאגר, CI, הגנת ענף, סביבת Staging והרשאת פרסום לגרסה המדויקת | Checks עוברים על ה־SHA שנבחר; אין הסתמכות על CI ישן |
| 2 | Vercel | צוות ופרויקט קיימים, Web, Origins וזהות שירות OIDC | Web מהגרסה הנבחרת מתקשר ל־API ומסרב לזהות שגויה |
| 3 | Railway | API, Workers בתפקידים נפרדים, PostgreSQL, Redis ורשת פרטית | אותה גרסה בכל השירותים, כל 93 המיגרציות עד 0092, Roles מצומצמים ובריאות תקינה |
| 4 | Clerk | אפליקציה, דומיינים, Organization, MFA והזמנות | הרשמה, כניסה, מעבר עסק, הזמנה וביטול הרשאה מוכחים |
| 5 | Meta / WhatsApp Business | App, Business portfolio, נכסים והרשאות, Embedded Signup/Coexistence, Webhooks ומספר מורשה | קוד/QR במסלול הרשמי שמציג Meta, הודעות וסנכרון במכשיר זכאי |
| 6 | AWS | S3 פרטי עם Versioning, KMS, GuardDuty ו־IAM נפרד להעלאה/סריקה/קריאה/מחיקה | העלאה, סריקה, הגשה ומחיקת גרסה מדויקת בהרשאות אמת |
| 7 | OpenAI | Project ומפתח Worker, מודל זמין, מחירון מתוארך ובקרת תקציב | Evals, עלות בפועל, Timeout ובירור; טיוטה מאושרת בלבד |
| 8 | Paddle | חשבון Sandbox, מוצר ומחיר אמיתיים, Client token, API ו־Webhook secret | Checkout, חתימה, זכאות, ביטול ו־Portal מוכחים ב־Sandbox |
| 9 | Better Stack | המקור וה־OTLP endpoint הקיימים, התראות ואחראי הסלמה | אירועי Web/API/Worker מגיעים ללא תוכן רגיש, והתראה מגיעה לאחראי |
| 10 | דומיין ו־DNS | לזהות בעלות וספק מתוך החשבון בפועל; לחבר Web/API ו־TLS | שמות אמיתיים, TLS ו־Origins תואמים; אין דומיין מומצא |

1.2 PostgreSQL ו־Redis הם משאבים בתוך Railway, ו־S3/KMS/GuardDuty בתוך AWS; אין צורך בסדרת חשבונות נפרדת לכל רכיב. דומיין מותאם אינו נרכש בלי בחירה קונקרטית של שם ומחיר. רשימת החיבורים נובעת מהקוד והתוכנית הקיימים; לא נוספו ספקי שירות חלופיים.

# 2. סדר הפעלה

2.1 להשלים את תת־שלב הביקורת C4.1.5. לבחור גרסת מסירה אחת ולוודא שאין פער קוד פתוח שהוסתר תחת “חיבור”.

2.2 לבדוק את גישת החשבונות ורק אחר כך להגדיר Staging מבודד. להעניק לכל שירות את סודותיו בלבד. הרשאות השחזור הן Logins פרטיים לפי [מדריך השחזור](../uncertain-outcome-recovery.md); אינן חלק מסודות ה־API.

2.3 להריץ Preflight, מיגרציות, בדיקת הרשאות ו־Restore. לפרוס קוראים תואמים ו־Workers מאותה גרסה, כשהמתגים של שליחה, העלאה, AI וחיוב עדיין כבויים.

2.4 להפעיל תהליך אחד בכל פעם: זהות → Meta/QR → Inbox/Templates/Campaign/Bot → מדיה → Knowledge/AI → Paddle. לשמור ראיות אמיתיות ולתקן ממצאי קבלה. אין להסתמך על תוצאת בדיקה מקומית כראיית ספק.

2.5 לבדוק עברית/אנגלית/ערבית, מכשיר נייד, נגישות, ניתוק וחזרה, עומס, התראות ושחזור. לאחר עמידה בתנאי ה־Master Plan: Pilot של 10 ימי עבודה ו־Canary של 72 שעות.

# 3. זמן וסטטוס

3.1 R223 סוגר קריאת היסטוריה קודמת אחרי Signup מאומת. נותרו ייבוא אצוות למחזור מוכח וביקורת מסירה — שני תתי־שלבים, 6–12 שעות הנדסה בביטחון נמוך. פירוט מחייב בסעיף 18 בתור השלמת הקוד. הרשאות API וקורא קבצים צריכות לכלול SELECT על `meta_history_read_authorizations`, ללא גישה לתוכן יומן האירועים שבבירור.

3.2 נותרו 12 שלבי השקה ראשיים. משך חיבור החשבונות, אישורי Meta והקבלה החיה אינו ידוע; אין מועד השקה מאומת. אומדני הבסיס המלאים ותתי־השלבים נשארים ב[Master Plan](launch-master-plan-2026-09-09.md), ולא מחושבים כאילו הם שעות עבודה שנמדדו.
